# Мониторинг телеметрии электротехнических устройств

Бакалаврский дипломный проект на Go. **Этап 1: минимальный сквозной контур.**

```text
Simulator → Mosquitto (MQTT QoS 1) → Ingestion → Kafka → Processor → TimescaleDB
                                                                      ↑
                                                                  REST API
```

Реализованы регистрация устройств, физически согласованная генерация,
валидация, карантин, доставка через Kafka, транзакционная дедупликация,
последние значения и история с курсорами. Есть JSON-логи, health endpoints
и Prometheus-метрики. Аварии, online/offline, агрегаты, Grafana и нагрузочные
испытания — следующие этапы, см. [архитектуру](docs/architecture/README.md).

## Требования

На машине нужны только **GNU Make и работающий Docker с Compose и Buildx**.
На Ubuntu используется Docker Engine, на Windows — Docker Desktop с Linux
containers. На Windows команду `make` можно заменить на `mingw32-make`.

Go 1.26.3, Bash, curl, jq, компилятор для race detector и инструменты проверки
находятся внутри контейнеров. Устанавливать их на хост для работы проекта не нужно.
Свободные порты: 1883, 5432, 8080–8083, 19092. Для комфортной работы стенда
рекомендуется выделить Docker 4 CPU и 6 ГБ RAM; это ориентир, не результат измерений.

Установка Docker на Ubuntu описана в
[официальной инструкции](https://docs.docker.com/engine/install/ubuntu/),
доступ пользователя к Docker — в [Linux post-install](https://docs.docker.com/engine/install/linux-postinstall/).
В WSL2 включите интеграцию Ubuntu с Docker Desktop. Папка проекта на диске D:
в WSL обычно доступна как `/mnt/d/diplom`.

## Запуск одной командой

Откройте терминал в корне проекта и выполните:

```bash
make run
```

Make соберёт контейнеры, запустит БД и брокеры, создаст Kafka topics, дождётся
готовности API, приёмника и обработчика и запустит непрерывный эмулятор.
Первый запуск загружает образы, Go-модули и зависимости, поэтому занимает больше времени.
При ошибке команда завершается с ненулевым кодом; ожидание readiness ограничено.

Команды одинаковы в Ubuntu, WSL2 и Windows. Чтобы изменить нагрузку:

```bash
make run DEVICES=100 INTERVAL=2s SEED=42
```

Проверить состояние и данные:

```bash
make ps
make devices
make latest DEVICE_ID=meter-000001
make history DEVICE_ID=meter-000001
make logs SERVICES=processor TAIL=50
```

`Ctrl+C` завершает просмотр логов. Для остановки стенда с сохранением данных:

```bash
make down
```

## Конечный прогон эмулятора

Если непрерывный эмулятор уже запущен, сначала остановите его:

```bash
make stop SERVICES=simulator
make simulate DEVICES=10 INTERVAL=1s ROUNDS=3 SEED=42
make latest
make history
```

`simulate` самостоятельно поднимает основные сервисы и ожидает готовности
приёмника. Он регистрирует устройства через API и отправляет по одному измерению
за раунд. MQTT PUBACK означает приём брокером, а не завершение записи в БД:
после конечного прогона дождитесь последней sequence через `make latest`.
Предыдущие данные сохраняются; session_id отличает запуски генератора.

Генератор использует одно MQTT-соединение и последовательную отправку.
Он пока не предназначен для доказательства 50 000 msg/s. Seed воспроизводит
физическую модель при одинаковых параметрах; идентификаторы и время меняются.

## Сборка и проверки

Все операции проекта запускаются через Makefile:

| Команда | Результат |
|---|---|
| `make help` | Список команд |
| `make config` | Проверка Compose-конфигурации |
| `make build` | Сборка образов приложений, эмулятора и инструментов |
| `make up` | Сборка и запуск основных сервисов с ожиданием readiness |
| `make run` / `make demo` | Запуск стенда и непрерывного эмулятора |
| `make wait` | Ожидание readiness основных сервисов |
| `make fmt` | Форматирование исходников в рабочей папке |
| `make test` | Unit-тесты в контейнере |
| `make vet` | Статическая проверка Go |
| `make check` | Unit-тесты и vet |
| `make test-race` | Race detector и vet |
| `make test-integration` | Запуск стенда и тесты реальных БД/MQTT/Kafka/API |
| `make smoke` | Запуск стенда, ожидание готовности и сквозные проверки |
| `make recovery` | Остановка обработчика, отправка сообщений и проверка восстановления |
| `make verify` | Последовательно check, test-race, smoke и recovery |
| `make restart SERVICES=processor` | Перезапуск выбранного сервиса и ожидание readiness |

Для полной проверки:

```bash
make verify
```

Make выполняет проверки последовательно, в том числе при передаче `-j`, поскольку
recovery останавливает processor. Не запускайте recovery параллельно с проверками
в другом терминале. Тесты создают устройства с префиксами e2e/recovery для ручной
проверки; тест хранения удаляет собственные данные.

Контейнер recovery получает Docker socket только на время проверки, чтобы
остановить/запустить processor. Обычные тестовые контейнеры socket не получают.
Проверки каждый раз выполняются заново; кешируются зависимости и Go-компиляция.

Корневой [Makefile](Makefile) управляет контейнерами. [build/Makefile](build/Makefile)
содержит команды сборки и проверок внутри них; Dockerfile также вызывает этот
Makefile для сборки Go-программ. Ручной запуск Go, Docker Compose и скриптов
в рабочем процессе не требуется.

## REST API

Машиночитаемый контракт: [OpenAPI 3.1](api/openapi.yaml).
Для ручного просмотра JSON можно открыть [список устройств](http://localhost:8080/api/v1/devices)
в браузере. Графического интерфейса оператора пока нет.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/v1/devices` | Регистрация: id, name, expected_interval_seconds |
| GET | `/api/v1/devices?limit=100&after=...` | Список, следующий курсор next_after |
| GET | `/api/v1/devices/{id}` | Устройство и last_seen_at |
| GET | `/api/v1/devices/{id}/latest` | Последнее измерение, 404 если данных нет |
| GET | `/api/v1/devices/{id}/measurements` | История по убыванию timestamp/message_id |

Параметры истории: from/to (RFC3339), limit (1–1000). По умолчанию последний час,
максимум 7 суток, интервал `[from,to)`. Если next не null, передайте before и
before_message_id из него и те же from/to в следующем запросе. last_seen_at пока
не преобразуется в online/offline.

Процессы предоставляют `/health/live`, `/health/ready`, `/metrics` на портах
8080/8081/8082/8083 (API/ingestion/processor/simulator). У генератора endpoints
доступны после регистрации устройств и MQTT-подключения, пока он работает.
Readiness процессора проверяет БД и Kafka, но не измеряет lag.

## Телеметрия и ограничения

MQTT 3.1.1, QoS 1, topic `devices/{device_id}/telemetry`.
Контракт полей и диапазонов: [JSON Schema](contracts/telemetry-v1.schema.json).
Проверяются возраст сообщения до 24 часов, опережение до 30 секунд, размер до
4096 байт, совпадение устройства с topic и регистрация устройства.
Мощность согласована с `P = U × I × cosφ` с погрешностью max(1 Вт, 2%).
Повторная отправка сохраняет все поля, включая message_id и timestamp.
Неизвестные устройства, некорректные данные и конфликты содержимого направляются
в `telemetry.invalid.v1`. Карантин содержит причину и ограниченный payload.

Named volumes переживают `make down`. Миграция 001 применяется только к пустому
PostgreSQL volume. Новые миграции существующей БД не применяются перезапуском.
Порты опубликованы на loopback; учебные учётные данные и MQTT без авторизации
предназначены для локального стенда на доверенной машине.

Это стенд с одним Kafka broker, MQTT broker и экземпляром БД. Гарантии и
ограничения отказоустойчивости: [архитектура](docs/architecture/README.md),
[ADR 001](docs/adr/001-initial-boundaries.md).
Нагрузочные результаты пока отсутствуют. Актуальный отчёт:
[проверка запуска через Makefile](docs/verification-make.md).
Историческая проверка первого среза: [этап 1](docs/verification-stage-1.md).
